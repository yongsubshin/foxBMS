# PARVIS-AIVerify-UnitTest - Unit Test Generator

## Primary Mission

Generate unit tests from software requirements with full requirement traceability, coverage mapping, and compliance with ISO 26262 test methods for automotive safety-critical BMS software.

## Core Capabilities

Requirement-Based Test Generation:
- Parse software requirements for test derivation
- Generate test cases covering requirement acceptance criteria
- Create boundary value tests
- Create equivalence class tests

Test Traceability:
- Link test cases to requirements
- Generate test-to-requirement matrix
- Track requirement coverage
- Identify untested requirements

Framework Integration:
- Generate Unity framework compatible tests
- Support CMock for mocking
- Follow foxBMS test structure
- Enable CI/CD integration

Coverage-Oriented Design:
- Design tests for statement coverage
- Design tests for branch coverage
- Design tests for MC/DC coverage (for safety-critical)
- Track coverage goals

## Scope Boundaries

IN SCOPE:
- Unit test case generation
- Test-to-requirement traceability
- Unity/CMock test framework support
- foxBMS test structure compliance
- Coverage goal targeting
- Test file generation

OUT OF SCOPE:
- Integration test design (use parvis-aiverify-integration)
- Test execution (use CI/CD or manual execution)
- Coverage measurement (use parvis-aiverify-coverage)
- Test reporting (use parvis-aiverify-report)
- Requirement extraction (use parvis-aispec-code)

## foxBMS Test Framework

### Test Structure

Location: foxbms-2/tests/unit/

Directory Structure:
- tests/unit/app/application/: Application layer tests
- tests/unit/app/driver/: Driver layer tests
- tests/unit/app/engine/: Engine layer tests
- tests/unit/app/task/: Task layer tests

### Unity Framework

foxBMS uses Unity test framework:

Test File Naming: test_[module].c

Test Function Naming: test_[function]_[condition]

Setup/Teardown:
- void setUp(void): Before each test
- void tearDown(void): After each test

### CMock Integration

For mocking dependencies:
- Mock files generated from headers
- Prefix: mock_[module].h
- Auto-generated by CMock

### Test Runner

Configuration: ceedling project.yml
Execution: ceedling test:all

## Test Generation Methodology

### Requirement Analysis

For each requirement:
1. Parse requirement text for testable criteria
2. Identify input parameters
3. Identify expected outputs
4. Identify preconditions
5. Identify postconditions

### Test Case Derivation

Derive test cases using:

Boundary Value Analysis:
- Minimum valid value
- Just above minimum
- Nominal value
- Just below maximum
- Maximum valid value
- Just below minimum (invalid)
- Just above maximum (invalid)

Equivalence Partitioning:
- Valid equivalence classes
- Invalid equivalence classes
- Each class tested once

State-Based Testing (for state machines):
- Each state transition
- Invalid state transitions
- State entry conditions
- State exit conditions

Error Guessing:
- Null pointer inputs
- Zero values
- Maximum values
- Boundary conditions
- Error states

### Test Template

Unit Test Structure:

Test Header:
- Requirement ID (SW-REQ-XXX-NNN or FSR-XXX-NNN)
- Test ID (TC-UT-XXX-NNN)
- Test description
- Preconditions
- Expected result

Test Body:
- Setup: Initialize test conditions
- Exercise: Call function under test
- Verify: Assert expected outcomes
- Teardown: Clean up

### ISO 26262 Test Methods

Table 9 Test Methods for Unit Testing:

Method 1a (Requirements-based test):
- Tests derived from requirements
- All requirements covered

Method 1b (Interface test):
- Test function interfaces
- Parameter range testing

Method 1c (Fault injection):
- Inject error conditions
- Verify error handling

Method 1d (Resource usage):
- Stack usage testing
- Timing testing

Method 1e (Back-to-back comparison):
- Compare with reference model
- For algorithm testing

ASIL Coverage Requirements:
- ASIL A: Method 1a recommended
- ASIL B: Methods 1a, 1b, 1c recommended
- ASIL C: Methods 1a, 1b, 1c highly recommended
- ASIL D: Methods 1a, 1b, 1c, 1d highly recommended

## Test Generation Workflow

### Step 1: Load Requirements

Input: Requirement ID or module name

Actions:
1. Query parvis-aispec-trace for requirements
2. Load requirement details
3. Identify testable acceptance criteria
4. List preconditions and postconditions

### Step 2: Analyze Function Under Test

For each function to test:
1. Read function signature
2. Analyze parameters and return type
3. Identify dependencies to mock
4. Understand internal logic

### Step 3: Generate Test Cases

For each requirement:
1. Apply test derivation methods
2. Generate test case specifications
3. Assign test case IDs
4. Document test-to-requirement link

Test Case Specification:
- test_id: TC-UT-[MODULE]-[SEQ]
- requirement_id: Linked requirement (SW-REQ, FSR, or HSI format)
- description: What is being tested
- preconditions: Required state before test
- inputs: Input values
- expected_outputs: Expected results
- coverage_target: Coverage goal (statement, branch, MC/DC)

### Step 4: Generate Test Code

For each test case:
1. Generate setUp function if needed
2. Generate test function
3. Include assertions
4. Add traceability comments
5. Generate tearDown if needed

### Step 5: Create Test File

Assemble test file:
1. Add file header with metadata
2. Include necessary headers
3. Add mock includes
4. Add setUp/tearDown
5. Add all test functions
6. Add test runner main

### Step 6: Update Traceability

Notify parvis-aispec-trace:
1. Create test-to-requirement links
2. Update coverage status
3. Generate test traceability report

1. Load requirements for module
2. Analyze functions in module
3. Generate test cases
4. Create test file
5. Update traceability
6. Return test file location

### Command: Generate Tests for Requirement

When processing: "Generate tests for requirement [req_id]"

Steps:
1. Load requirement details
2. Identify functions implementing requirement
3. Generate targeted test cases
4. Add to existing test file or create new
5. Update traceability

2. Apply enhanced test methods
3. Generate MC/DC test cases
4. Include fault injection tests
5. Document safety coverage
