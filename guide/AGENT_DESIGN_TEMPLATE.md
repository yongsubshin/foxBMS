# BMS 안전 표준 준수 에이전트 설계 템플릿

이 문서는 자동차 안전 표준(ISO 26262, MISRA C, ASPICE, V-Model)을 준수하는 에이전트를 설계하기 위한 템플릿입니다.

---

## 1. 요구사항 분석 에이전트 (Requirement Analysis Agent)

### 목적
기능 요구사항을 분석하고 ASIL 수준을 결정하여 안전 요구사항을 도출합니다.

### 입력
- 사용자 기능 설명
- 시스템 컨텍스트
- 안전 제약사항

### 처리 프로세스

1. **기능 분석**
   - 기능을 구체적인 요구사항으로 변환
   - Severity, Exposure, Controllability 분석

2. **ASIL 결정**
   - ASIL 매트릭스 적용
   - ASIL A/B/C/D 결정
   - 근거 기록

3. **안전 요구사항 도출**
   - 기능 요구사항에서 안전 요구사항 추출
   - 진단 요구사항 정의

4. **초기 FMEA**
   - 고장 모드 식별
   - 원인 및 영향 분석
   - RPN 계산

### 출력물

```
요구사항 문서 (SRS):
├── 기능 요구사항
│  ├── REQ_BMS_CHRG_001: [설명]
│  ├── REQ_BMS_CHRG_002: [설명]
│  └── ...
├── 안전 요구사항
│  ├── REQ_BMS_SAFE_001: 과충전 감지 및 차단
│  └── ...
├── ASIL 분석
│  ├── REQ_BMS_CHRG_001: ASIL C
│  └── ...
└── 초기 FMEA
   ├── 고장 모드: 과충전
   ├── 원인: 충전 제어 오류
   ├── 영향: 배터리 손상, 화재
   ├── S: 5, O: 3, D: 3 → RPN: 45
   └── ...
```

### 검증 기준
- [ ] 모든 기능이 요구사항으로 변환됨
- [ ] ASIL 결정이 명확히 기록됨
- [ ] 모든 요구사항에 ID 부여됨
- [ ] FMEA가 완성됨

## 2. 설계 에이전트 (Design Agent - Architecture)

### 목적
요구사항을 시스템 아키텍처로 변환합니다.

### 입력
- 요구사항 문서 (SRS)
- 초기 FMEA
- 하드웨어 제약사항

### 처리 프로세스

1. **아키텍처 설계**
   - 주요 컴포넌트 정의
   - 컴포넌트 간 인터페이스 설계
   - 제어 흐름 정의

2. **안전 메커니즘 설계**
   - FMEA 기반 안전 장치 설계
   - 고장 격리 메커니즘
   - 감시 메커니즘

3. **추적성 매트릭스 작성**
   - 요구사항 → 설계 매핑

4. **FMEA 업데이트**
   - 설계 기반 FMEA 개선

### 출력물

```
아키텍처 설계서:
├── 시스템 블록 다이어그램
│  ├── MCU (Main Controller)
│  ├── Sensor Module (전압, 온도, 전류)
│  ├── Power Management Module
│  └── Communication Module (CAN)
├── 컴포넌트 명세
│  ├── DES_BMS_MCU_001: MCU 선택 및 요구사항
│  ├── DES_BMS_SENSOR_001: 센서 이중화 설계
│  └── ...
├── 인터페이스 정의
│  ├── SPI: MCU ↔ ADC
│  ├── CAN: BMS ↔ 차량 네트워크
│  └── ...
├── 안전 메커니즘
│  ├── 이중 MCU (Lockstep)
│  ├── 센서 이중화
│  ├── 하드웨어 차단 회로
│  └── ...
└── 요구사항-설계 추적성 매트릭스
   ├── REQ_BMS_CHRG_001 → DES_BMS_MCU_001
   └── ...
```

### 검증 기준
- [ ] 모든 요구사항이 설계로 매핑됨
- [ ] 안전 메커니즘이 FMEA 기반으로 설계됨
- [ ] 컴포넌트 간 인터페이스가 명확함
- [ ] 추적성 매트릭스가 완성됨

## 3. 구현 에이전트 (Implementation Agent)

### 목적
설계를 MISRA C 준수 코드로 구현합니다.

### 입력
- 아키텍처 설계서
- 모듈 설계 명세
- 코딩 표준 (MISRA C:2012)

### 처리 프로세스

1. **코드 생성**
   - MISRA C 준수 코드 작성
   - 함수 프로토타입 정의
   - 에러 처리 구현

2. **정적 분석**
   - LDRA/QAC 실행
   - MISRA C 규칙 위반 검사
   - 코드 커버리지 분석

3. **코드 리뷰**
   - 안전 중요 코드 검토
   - 추적성 검증

### 출력물

```
소스 코드:
├── bms_main.c
│  ├── main()
│  ├── Init_BMS()
│  └── Monitor_BateryStatus()
├── bms_charging.c
│  ├── Charging_Control()
│  ├── OverCharge_Protection()
│  └── ...
├── bms_diagnostic.c
│  ├── DTC_Log()
│  ├── Self_Diagnostic()
│  └── ...
└── bms_safety.c
   ├── Safety_Check()
   ├── Fault_Isolation()
   └── ...

정적 분석 리포트:
├── MISRA C 위반 항목: 0
├── 경고: 5 (허용범위)
├── 에러: 0
└── 코드 커버리지: 87%

코드-설계 추적성 매트릭스:
├── DES_BMS_MCU_001 → bms_main.c/Init_BMS()
└── ...
```

### 검증 기준
- [ ] 모든 설계가 코드로 구현됨
- [ ] MISRA C 필수 규칙 100% 준수
- [ ] MISRA C 권장 규칙 95% 이상 준수
- [ ] 정적 분석 에러 0개
- [ ] 코드 커버리지 ≥ 85%

## 4. 테스트 에이전트 (Test Agent)

### 목적
테스트 계획 수립 및 테스트 케이스 생성 및 실행합니다.

### 입력
- 요구사항 문서 (SRS)
- 소스 코드
- V-Model 테스트 전략

### 처리 프로세스

1. **테스트 전략 수립**
   - V-Model 기반 테스트 계획
   - 테스트 유형 정의 (단위, 통합, 시스템)

2. **테스트 케이스 생성**
   - 각 요구사항에 대응하는 테스트 케이스
   - 정상 케이스 + 경계 케이스 + 오류 케이스

3. **테스트 실행**
   - 자동화 테스트 실행
   - 결과 수집 및 분석

4. **커버리지 분석**
   - 코드 라인 커버리지 계산
   - 분기 커버리지 확인

### 출력물

```
테스트 계획서:
├── 테스트 전략
│  ├── 단위 테스트: 각 함수별
│  ├── 통합 테스트: 모듈 간 인터페이스
│  └── 시스템 테스트: 전체 시스템
├── 테스트 환경
│  ├── 하드웨어: STM32 개발보드
│  ├── 소프트웨어: Unity, CMock
│  └── 도구: Gcov (커버리지 분석)
└── 일정 및 책임자

테스트 케이스:
├── TEST_BMS_UNIT_001
│  ├── 기능: ReadCellVoltage()
│  ├── 입력: 셀 인덱스 [0, 11]
│  ├── 예상 출력: 유효한 전압값
│  ├── 실제 결과: PASS
│  └── 날짜: 2025-12-15
├── TEST_BMS_UNIT_002
│  ├── 기능: OverChargeProtection()
│  ├── 입력: 셀 전압 4.3V
│  ├── 예상 출력: 충전 중단, 알람 발생
│  ├── 실제 결과: PASS
│  └── 날짜: 2025-12-15
└── ...

테스트 결과 리포트:
├── 총 테스트 케이스: 45
├── 통과: 45
├── 실패: 0
├── 코드 커버리지: 87%
│  ├── 라인 커버리지: 87%
│  └── 분기 커버리지: 82%
└── 결론: 기준 충족

코드-테스트 추적성 매트릭스:
├── bms_main.c/Init_BMS() → TEST_BMS_UNIT_003
└── ...
```

### 검증 기준
- [ ] 모든 요구사항에 대응하는 테스트 케이스 존재
- [ ] 모든 테스트 케이스 통과
- [ ] 코드 커버리지 ≥ 85%
- [ ] 추적성 매트릭스 완성

## 5. 검증 에이전트 (Safety Verification Agent)

### 목적
ASIL 달성 여부를 검증합니다.

### 입력
- 완성된 FMEA
- 테스트 결과
- 코드 정적 분석 결과

### 처리 프로세스

1. **최종 FMEA 검증**
   - 모든 고장 모드가 감지 또는 제어되는지 확인
   - RPN < 100 달성 확인

2. **ASIL 달성 확인**
   - 각 ASIL C/D 요구사항이 구현되었는지 검증
   - 안전 메커니즘 동작 확인

3. **진단 기능 검증**
   - DTC 로깅 기능 확인
   - 자체 진단 기능 확인

4. **요구사항 완료 확인**
   - 모든 요구사항이 테스트를 통과했는지 확인

### 출력물

```
안전 검증 리포트:
├── FMEA 최종 검증
│  ├── 총 고장 모드: 15
│  ├── 감시됨: 15 (100%)
│  ├── RPN < 100: 15 (100%)
│  └── 미해결 항목: 0
├── ASIL 달성 확인
│  ├── ASIL C 요구사항: 12
│  ├── 구현됨: 12 (100%)
│  ├── 테스트 통과: 12 (100%)
│  └── 결론: ASIL C 달성
├── 진단 기능 검증
│  ├── DTC 코드 정의: 25
│  ├── 로깅 기능: 구현됨
│  ├── 자체 진단: 구현됨
│  └── 결론: 통과
└── 안전 결론
   └── 이 소프트웨어는 ISO 26262 ASIL C 요구사항을 만족합니다.
```

### 검증 기준
- [ ] 모든 FMEA 항목이 처리됨
- [ ] ASIL 달성 요구사항 100% 충족
- [ ] 진단 기능이 완전히 구현됨
- [ ] 검증 리포트 작성 완료

## 6. 추적성 에이전트 (Traceability Agent)

### 목적
요구사항에서 테스트까지 완전한 추적성을 유지합니다.

### 입력
- 요구사항 문서
- 설계서
- 소스 코드
- 테스트 케이스

### 처리 프로세스

1. **추적성 매트릭스 생성**
   - 요구사항 → 설계 매핑
   - 설계 → 코드 매핑
   - 코드 → 테스트 매핑

2. **누락 검사**
   - 요구사항이 누락된 설계 확인
   - 설계가 누락된 코드 확인
   - 코드가 누락된 테스트 확인

3. **변경 영향도 분석**
   - 요구사항 변경 시 영향받는 설계, 코드, 테스트 파악

### 출력물

```
완전한 추적성 매트릭스:

┌─────────────────────────────────────────────────────────────────────┐
│ 요구사항 │ 설계 │ 코드 │ 테스트 │ 상태 │ 커버리지 │
├─────────┼──────┼──────┼────────┼──────┼──────────┤
│REQ_BMS_ │DES_  │bms_  │TEST_   │PASS  │ 100%     │
│CHRG_001 │MCU_  │charg │BMS_    │      │          │
│         │001   │ing.c │UNIT_   │      │          │
│         │      │      │001     │      │          │
│         │      │      │        │      │          │
│REQ_BMS_ │DES_  │bms_  │TEST_   │PASS  │ 100%     │
│SAFE_001 │SAFE_ │safe  │BMS_    │      │          │
│         │001   │ty.c  │UNIT_   │      │          │
│         │      │      │002     │      │          │
└─────────┴──────┴──────┴────────┴──────┴──────────┘

누락 검사 결과:
├── 미매핑 요구사항: 0
├── 미구현 설계: 0
├── 미테스트 코드: 0
└── 결론: 100% 추적성 달성

변경 영향도 분석:
├── 요구사항 변경: REQ_BMS_CHRG_002
├── 영향받는 설계: DES_BMS_MCU_002
├── 영향받는 코드: bms_charging.c (5개 함수)
├── 영향받는 테스트: TEST_BMS_UNIT_003, 004, 005
└── 예상 영향도: 중간
```

### 검증 기준
- [ ] 모든 요구사항이 설계로 매핑됨
- [ ] 모든 설계가 코드로 구현됨
- [ ] 모든 코드가 테스트로 검증됨
- [ ] 누락된 항목 없음

## 7. 규정 준수 에이전트 (Compliance Agent)

### 목적
최종 규정 준수를 검증하고 보고서를 생성합니다.

### 입력
- 모든 산출물 (요구사항, 설계, 코드, 테스트, 검증)
- 정적 분석 결과
- ASPICE 평가 결과

### 처리 프로세스

1. **ISO 26262 준수 검증**
   - Part 6 (소프트웨어) 요구사항 확인
   - ASIL C/D 달성 확인

2. **MISRA C 준수 확인**
   - 필수 규칙 100% 준수 확인
   - 권장 규칙 95% 이상 준수 확인

3. **ASPICE 레벨 평가**
   - 프로세스 성숙도 평가
   - 필수 작업 산출물 완성 확인

4. **최종 규정 준수 선언**
   - 종합 규정 준수 리포트 작성

### 출력물

```
최종 규정 준수 리포트:

1. ISO 26262 준수 선언
   ├── 표준 버전: ISO 26262:2018
   ├── 적용 범위: BMS 소프트웨어 (Part 6)
   ├── ASIL 수준: ASIL C
   ├── 준수 상태: 준수 ✓
   └── 세부사항:
       ├── 요구사항 분석: 완료 ✓
       ├── 설계: 완료 ✓
       ├── 구현: 완료 ✓
       ├── 검증: 완료 ✓
       ├── 추적성: 완료 ✓
       └── 문서화: 완료 ✓

2. MISRA C:2012 준수 선언
   ├── 준수 상태: 준수 ✓
   ├── 필수 규칙: 143/143 (100%)
   ├── 권장 규칙: 95% (정적 분석 도구 결과)
   ├── 위반 항목:
   │  ├── MISRA C 규칙 위반: 0
   │  ├── 정적 분석 에러: 0
   │  └── 경고: 5 (모두 정당화됨)
   └── 보안 가이드라인 (Amendment 1): 준수 ✓

3. ASPICE 4.0 평가
   ├── 평가 수준: Level 2
   ├── SWE 프로세스: 2/2 달성
   │  ├── SWE.1 (요구사항): Level 2 ✓
   │  ├── SWE.2 (아키텍처): Level 2 ✓
   ├── SUP 프로세스: 필수 지원 완료 ✓
   │  ├── SUP.1 (품질 보증): ✓
   │  ├── SUP.7 (문서화): ✓
   │  └── SUP.8 (형상 관리): ✓
   └── 결론: Level 2 달성

4. 품질 지표
   ├── 코드 커버리지: 87% (≥85% 요구)
   ├── 테스트 통과율: 100% (45/45)

   └── 이 BMS 소프트웨어는 다음을 준수합니다:

```
